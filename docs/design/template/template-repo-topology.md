## Problem Statement

The public template at `sunholo-data/ai-protocol-platform` is **generated by
subtraction**: [scripts/sanitize-for-template.sh](../../../scripts/sanitize-for-template.sh)
takes this repo's tree, deletes what must not ship, rewrites what must not be
named, and force-pushes the residue. That script is now **1154 lines with ~120
token-replacement rules and three security gates**, and it is losing.

**Current State:**

| Measure | Value |
|---|---|
| Commits in last 90 days | 752 |
| …touching **no** customer path | **673 (89%)** |
| Tracked files following the `one-*` customer convention | 19 |
| Files that survive the delete lists but are **rewritten in content** | **337** |
| Sanitize script | 1154 lines, ~120 scrub rules, 3 gates |

Nine of ten commits are template work. We run a subtractive pipeline over a repo
that is ~90% template, and the script's own comment history reads as an
incident log:

- **`one-bigquery`'s `SKILL.md` was missed** (2026-08-12) — its two design docs
  were added to `DELETE_PATHS` by hand; the file next to them carrying the
  customer's entire BigQuery schema was not. The gate caught it. The
  *mechanism* did not.
- **Two forks' business plans were published** — the internal-tools fork
  [#10](#evidence-from-the-the internal-tools fork-fork): `docs/design/forks/` shipped a named
  private individual's unlaunched product plan, and a client collective's own scope doc
  (staff names, EUR business case) to every other forker. This is squarely
  inside the [CLAUDE.md](../../../CLAUDE.md) hard rule that opens the repo, and
  the pipeline shipped it anyway.
- **UAT meeting minutes** with two customer employees by name, verbatim quotes,
  and a live sales pipeline passed **all three gates** — zero `acmeenergy`
  spellings in the file.
- **Customer staff names had spread into shipping source** — ~10 comments in
  `ChatShell.tsx`, `compareLauncher.ts`, `workbenchFocus.ts`, and a real full
  name as an email local-part in `AnalyticsPage.test.tsx`.

Every one of these is the same class: **a subtractive pipeline can only remove
what someone remembered to name.**

Two further problems compound it:

**The deploy tier has no home.** the internal-tools fork
[#17](#evidence-from-the-the internal-tools fork-fork) states it precisely — *"Upstream keeps
its Terraform in a separate private repo, so the state bucket and backend
bootstrap live there and never shipped. What the template ships are
compensations for a fork having no Terraform at all — not a bootstrap that hands
off to Terraform."* Twelve of the internal-tools fork's round-2 entries (#15–#26) are
first-deploy bootstrap failures in a tier that nobody owns: a Terraform root
that cannot create its own state bucket, IAM granted to a service account
nothing creates, a service running as the default compute SA, seven
prerequisites discovered one failed build at a time.

**Design docs are published incoherently.** the internal-tools fork
[#11](#evidence-from-the-the internal-tools fork-fork): of 55 `docs/design/` paths referenced
from `CLAUDE.md`, `backend/`, `frontend/src` and `.claude/skills/` in the
published template, **only 20 resolve.** The sanitizer deletes docs that
surviving files link to (a whole `v6.14.0/` is referenced and absent). These
pointers exist precisely so a fork reads the rationale instead of re-deriving
it — a dead link sends them back to re-deriving, which is the failure the doc
was written to prevent.

**Impact:**

- **Confidentiality** — the failure mode is publishing third parties'
  confidential material. It has already happened twice.
- **Forks** — the internal-tools fork and AIPLA carry a combined ~70-entry friction log, and
  the deploy-tier half of it has no upstream that can fix it.
- **Us** — every refresh is a manual sweep the gates cannot replace ("a green
  gate is necessary, not sufficient" is written into the publish skill).

### Evidence from an internal-tools fork

the internal-tools fork (`client-collective/the internal-tools fork`) is mid-bootstrap and keeps a friction log at
`docs/upstream-feedback.md` (#1–#11, closed) and `docs/upstream-feedback-v6.20.0.md`
(#12–#26, open). Its round-1 headline is the thesis of this document:

> **If you read one thing: the publish step doesn't validate what it emits.**
> Entries #8, #10 and #11 are three symptoms of one missing gate… The repo
> gates *deploys* on smoke tests that fail the build on any non-200, and gates
> `google-adk` bumps on `make adk-conformance`. Publishing the template — the
> artefact every downstream fork inherits, and the one place a confidentiality
> mistake reaches third parties — has no equivalent gate.

Its Appendix A is the other half of the answer, and it is **already proven**:
the internal-tools fork reconstructed a merge base from its seed commit and merged a template
refresh — **86 template files changed, 2 conflicts, CI green**, including a file
where upstream's fix and theirs were non-overlapping edits to the same function
and both survived. A hand-diff would have had to spot that by eye across 86
files. This design makes that ancestry *real* rather than reconstructed.

## Goals

**Primary Goal:** Make the template the upstream source of truth and this repo a
downstream consumer, so publishing is **one folder glob** instead of a
1154-line subtractive filter — and confidentiality holds **by absence** rather
than by remembering to name things.

**Success Metrics:**
- `scripts/template-parity.sh` reports **0** files differing by content
  (from **337**, measured 2026-08-17) — this is the go/no-go gate for the flip
- Publish tooling drops from **1154 lines → ~50** (one exclusion rule + the
  secret gate as backstop)
- Design-doc link resolution in the published tree: **20/55 → 55/55**, enforced
  by CI (the internal-tools fork #11)
- Deploy-tier bootstrap has an owner: the internal-tools fork #15–#26 become fixable upstream
- A template refresh for a fork is `git merge upstream/main`, not
  clone-and-hand-diff

**Non-Goals:**
- **Path restructuring.** No `core/` prefix, no subtree. Paths stay identical
  across all three tiers or the merge model collapses.
- **Rewriting this repo's history into the public repo.** See
  [History seeding](#history-seeding-genesis-only-never-filter-repo).
- **Changing what the platform does at runtime.** Zero behaviour change; this
  is topology, moves, and CI.
- **Solving fork licensing.** Flagged as an open question, not decided here.

## Design

### Overview

Three tiers, two publish/merge edges, one exclusion rule. A new **private
source-of-truth repo** holds the whole template including a `deploy/` folder for
the cloud tier. The **public repo** is published from it by excluding
`deploy/**` — one glob. **This repo** becomes a downstream consumer that merges
from source and adds only customer content.

```
       sunholo-data/platform-source            ← SOURCE OF TRUTH (private)
          (whole template + deploy/ tier)
                     │
      ┌──────────────┼───────────────────────────────┐
      │ publish      │ merge down                    │ merge down
      │ (exclude     │                               │
      │  deploy/**)  │                               │
      ▼              ▼                               ▼
 sunholo-data/   sunholo-data/ai-protocol-platform          client-collective/the internal-tools fork
 ai-protocol-    (this repo — customer ONE)    cphu/aipla-app
 platform                                      (commercial forks: need deploy/)
 (public)
      │
      │ "Use this template"
      ▼
 OSS / workshop forks (laptop tier)
```

Why a **third** repo rather than just promoting the public one to upstream: the
user-facing requirement is that the template covers *both* "runs on your own
laptop, open source" *and* "deploys to GCP with Terraform". Those cannot live in
one public repo without either publishing the deploy tier or amputating it. A
private source-of-truth repo holds both; the public repo is a **projection** of
it.

**Both upstream repos live in `sunholo-data`, not `Aitana-Labs`** (decided
2026-08-17). The org boundary now carries the actual meaning of the split:

- **`sunholo-data`** = the product. Template source and its public projection,
  licensed outward to commercial forks. Nothing here is Aitana's.
- **`Aitana-Labs`** = one deployment of that product, with its customer.

Keeping the source of truth beside its own projection also means org-level
access, teams and licensing are set once, in one place, rather than granting an
external fork access into the org that holds Aitana's customer work.

Critically, `platform-source` is private for **commercial** reasons, not
confidentiality ones. It contains no customer content and no Aitana deployment
identity — both live downstream. A leak from it would be embarrassing, not an
incident. That property is what makes it safe to hand to commercial forks — and
what makes `sunholo-data` the right org for it.

### Tier definition — the one glob

```
platform-source/
├── backend/            ─┐
├── frontend/            │
├── cli/                 │  PUBLIC TIER
├── infrastructure/      │  published verbatim to sunholo-data/ai-protocol-platform
│   ├── mcp-sandbox/     │  laptop-runnable via LOCAL_MODE=1
│   ├── mcp-toolbox/     │
│   └── mcp-ext-apps-map/│
├── docs/design/         │  ← design docs live HERE (see below)
├── docs/workshop/       │
├── .claude/skills/     ─┘
│
└── deploy/             ── PRIVATE TIER — never published
    ├── terraform/         roots, modules, + create-tf-state-bucket.sh (the internal-tools fork #17)
    ├── cloudbuild/        cloudbuild.yaml, cloudbuild.promote.yaml, per-service pipelines
    ├── scripts/           bootstrap-env.sh, bootstrap-gcp-project.sh, create-*.sh,
    │                      promote-env.sh, smoke-deployed.sh
    └── docs/              promotion.md, deployment-models.md, env-cut runbooks
```

**Publish rule, in full:**

```bash
git ls-files -z | grep -zv '^deploy/' | tar --null --files-from=- -cf - | tar -xf - -C "$OUT"
```

That is the entire content decision. Everything else in the current sanitizer
either disappears (token scrubbing — see the parity precondition) or moves to CI
in `platform-source` (the gates).

### The precondition: parity, or none of this works

The current pipeline does two different things and only one survives an
inversion:

- **Deletions** (`DELETE_PATHS`, `GLOB_DELETIONS`) — fine. In an
  upstream/downstream model these files simply don't exist upstream. Additive,
  no conflict, ever.
- **Value replacement** (the ~120-rule `TOKEN_REPLACEMENTS` table) — **fatal.**
  `your-project-id` → `your-project-id`, `acmeenergy.com` →
  `acme-energy.example`, `Dana` → `Dana`. These are *the same file with
  different content* on each side. Under any merge-based model that is a
  permanent conflict on every sync, forever.

So the invariant this whole design rests on:

> **platform-source ⊃ public** (differs only by *deleted folders*), and
> **downstream ⊃ platform-source** (differs only by *added files*). No file
> exists in two tiers with different content.

Which means all identity must be config-driven, and config holding real values
must be a **downstream-only file** where upstream ships only `.example`.

**Measured, not estimated (2026-08-17).** Running the sanitizer and diffing
file-by-file gives **337** files that exist in both trees with different
content. An earlier grep-based estimate of 105 counted only *customer* tokens
and missed the deployment-identity rules, which are the larger half:

| Token class | Files touched | Files where it's the *only* cause |
|---|---:|---:|
| Deployment identity (`your-project-id-*`, `platform`, `yourcompany.com`, emails, billing/folder ids) | 216 | 128 |
| Customer identity (`acmeenergy`, MarketData, counterparties, staff names) | 128 | 78 |
| Client names (the internal-tools fork/the internal-tools fork, a tutoring fork, long-stream, the client contact) | 38 | 14 |
| Local paths (`<local-path>`) | 31 | 11 |
| Repo URL (`sunholo-data/ai-protocol-platform`) | 18 | 2 |
| Live Cloud Run URLs | 17 | 0 |
| NDA-preview tells | 6 | 1 |

(95 files are hit by more than one class, so the columns overlap.)

The good news is that most are cosmetic —

```
backend/adk/callbacks.py:60         # comment example: "yourcompany.com and acmeenergy.com"
AccessControlEditor.tsx:94          placeholder="acmeenergy.com"
backend/auth/admin_roles.py:39      docstring: ``tenant-admin:acmeenergy.com``
cli/aiplatform/commands/bq.py:46    _DATA_PROJECT = "your-entsoe-project"   ← genuinely functional
```

Comments, placeholders and test fixtures that use the customer or our own
project as the worked example.

**The scrub table is already a working, tested specification of the fix.** The
sanitizer performs exactly this transformation today and the sanitized tree's
test suites pass — it replaces both sides of every assertion. So Phase 1 is
mostly *applying the existing table to the source tree permanently*, not
deriving what to change. The genuinely new work is the small set of files that
must hold **real** values for Aitana's own deploys (`cloudbuild.yaml`,
`backend/Makefile`, `.env.example`, `firestore.rules`, `_env.py`,
`deployed-urls.md`): those become downstream-only, with upstream shipping
`.example`. Every gap file gets one of three dispositions — **scrub in place**
(ships upstream, neutral value is fine), **move downstream** (customer/ops
content — cheaper than genericizing), or **config-drive** (needs a real value
here and a placeholder upstream).

[backend/db/local_fixture.py](../../../backend/db/local_fixture.py) already
degrades gracefully when the `one-*` templates are absent, and the
customer-touching tests already `pytest.skip` when their fixtures are missing —
the additive model is **already proven** in this repo.

### Design docs move upstream

Confirmed decision: platform design docs are confusing downstream for forks, and
the internal-tools fork #11 shows the published copy is incoherent anyway.

| Content | Home | Published? |
|---|---|---|
| Platform design docs (`docs/design/v6.*`, `docs/design/template/`) | `platform-source` | Yes |
| Deploy-tier docs (promotion, env-cut, deployment-models) | `platform-source/deploy/docs/` | No |
| **Fork** scope docs | that fork's own repo | n/a |
| **Customer** docs (ONE) | this repo, `docs/customers/` | n/a |
| UAT / user-acceptance records | this repo only, never upstream | n/a |

Link resolution becomes correct **by construction** — nothing is deleted between
authoring and publishing — and a CI link-check keeps it that way.

The fork-scope rule already has precedent: the internal-tools fork's scope doc was moved to their
repo on 2026-07-29 with the reasoning *"one owner per document."* This
generalises it and makes it enforceable (`docs/design/forks/` may not exist in
`platform-source` at all).

### Gates invert: publish-time filter → commit-time refusal

| Gate | Today | After |
|---|---|---|
| Secret patterns (`AIzaSy`, SA keys, tokens) | publish-time, exit 3 | CI in **all** repos + publish backstop |
| Customer identifiers | publish-time scrub + gate, exit 4 | CI in `platform-source` — any match fails the build (nothing customer-specific belongs there) |
| NDA-preview tells | publish-time, exit 5 | CI in `platform-source` |
| Fork scope docs | *(none — this is the internal-tools fork #10)* | **new**: path deny-rule, `docs/design/forks/**` cannot exist |
| Doc link resolution | *(none — this is the internal-tools fork #11)* | **new**: link-check over `docs/` + `CLAUDE.md` + `.claude/skills/` |
| `implemented/` honesty | *(none — this is the internal-tools fork #8)* | **new**: a doc under `implemented/` must reference code that exists |

This is a genuinely **weaker moment of enforcement** — a mistake committed to
`platform-source` is one push from public, with no staging tree in between. That
is the honest cost. It is offset by the fact that customer content never exists
in that checkout at all, so the mistake has to be *authored*, not merely
*forgotten*.

### Sync mechanism: real git ancestry

the internal-tools fork already proved the merge works with a *reconstructed* base. This makes
it real:

```bash
# one-time, in this repo, after Phase 1 parity reaches 0
git remote add upstream git@github.com:sunholo-data/platform-source.git
git fetch upstream
git merge --allow-unrelated-histories upstream/main   # painless: contents are identical
# thereafter
scripts/upstream-merge.sh        # git fetch upstream && git merge upstream/main
```

The graft is painless *because* Phase 1 made contents byte-identical: with an
empty common ancestor, git only conflicts where both sides have the same path
with different content.

**Caveat, straight from the internal-tools fork's Appendix A:** upstream deletions propagate
and git stages them **with no conflict, so they are silent** — that refresh
silently removed `docs/projects/the internal-tools fork-ai-assistant/`, the fork's *own* content
that happened to be in its seed. `scripts/upstream-merge.sh` must print staged
deletions for review before committing. Per the [Automation
Principle](../../../CLAUDE.md), this is a script + `make upstream-merge`, not a
documented manual sequence.

**Working rule:** template-owned paths are **read-only** in this repo except
during a merge. A platform fix discovered while working here gets made in
`platform-source` and merged down — not fixed here and cherry-picked up, which
produces duplicate commits that conflict on the next merge. A `git worktree`
against a shared `.git` makes the round-trip cheap.

### History seeding: genesis only, never filter-repo

`platform-source` starts from a **single genesis commit** containing today's
sanitized tree. It does **not** inherit this repo's 750-commit history via
`git filter-repo`.

This is a security decision, not a convenience one: path filtering cannot reach
**token-level** residue in historical diffs. Customer names inside older
versions of files that legitimately ship (`ChatShell.tsx`, the test fixtures,
the design docs) would survive any path-based rewrite and go public in history.

The public repo `sunholo-data/ai-protocol-platform` is **reused** rather than
recreated — its history is a single force-pushed commit today, so adopting it as
genesis costs nothing and preserves stars, existing forks, and its
Template-Repository status. Force-pushing stops; it gets a real, mergeable
history from that commit on. That alone is a large win for the four existing
forks, who currently cannot merge at all.

### CLI Surface

Per the design-doc checklist: **no new `aiplatform` commands.** These are
repo-maintenance operations for platform maintainers, not developer touchpoints
for a fork — and the publish tooling is itself excluded from what ships, so a
CLI command for it would be dead weight in every downstream. They land as
scripts + `make` targets:

| Target | Script | Purpose |
|---|---|---|
| `make template-parity` | `scripts/template-parity.sh` | Assert deletions-only; print content-differing files |
| `make upstream-merge` | `scripts/upstream-merge.sh` | Fetch + merge upstream, print staged deletions |
| `make publish-public` | `scripts/publish-public.sh` | Exclude `deploy/**`, run secret gate, push |

## Migration & Rollout

**Database Migrations:** None. No runtime, schema, or Firestore change.

**Feature Flags:** None. Phases 0–2 are ordinary commits to `dev` in this repo
and change nothing observable. The flip is Phase 3–4, atomic per repo.

**Rollback Plan:** Phases 0–2 are normal revertible commits. Phase 3 creates a
new repo and touches nothing existing. Phase 4 is the only one-way door — but
until `sanitize-for-template.sh` is deleted (last step of Phase 4) the old
pipeline still works, so rollback is "keep using it."

**Environment Variables:** New env-driven values replacing hardcoded identity
(e.g. the BigQuery data project in `bq.py`). Each gets a documented default and
a `.example` entry; no deployed env changes value.

## Security Considerations

- **The core security argument:** confidentiality moves from *filtering* to
  *absence*. Customer content never exists in `platform-source`, so the
  published tree cannot contain it regardless of who remembered what. This is
  what [CLAUDE.md](../../../CLAUDE.md)'s hard rule means by "architectural, not
  advisory."
- **Weaker enforcement moment, accepted knowingly.** A bad commit in
  `platform-source` is one push from public. Mitigated by CI gates on every PR
  plus a pre-push hook running the same regexes. Stated here so it is a decision,
  not a surprise.
- **No history rewrite.** Genesis commit only — path filtering cannot strip
  token-level residue from historical diffs. See
  [History seeding](#history-seeding-genesis-only-never-filter-repo).
- **The secret gate stays in the publish path** as a backstop even though CI
  should have caught it first. It costs one grep and it has already saved us
  once (2026-07-29, the inline dev Web API key in `verify_admin_scope_live.py`).
- **Firebase Web API keys remain permanently excluded** — unchanged, and now
  structurally so: `backend/scripts/_env.py` is a downstream-only file that
  never exists upstream.

## Performance Considerations

Not applicable — no runtime path is touched. The one measurable cost is
maintainer round-trip: a platform fix discovered while working downstream now
requires a commit upstream plus a merge, rather than one commit. Mitigated by
`git worktree` against a shared `.git`, and offset against the current cost of a
full manual sweep on every refresh.

## Open Questions

1. **Does the public tier keep a deploy story at all?** Recommendation: yes, but
   a *single-env, single-command* `gcloud run deploy` path that is complete and
   tested — no Terraform, no multi-env, no promotion. the internal-tools fork #21 (seven
   prerequisites discovered one build at a time) is what a half-deploy story
   costs. The alternative — laptop-only public tier — is cleaner but strands
   existing OSS forks that already deploy.
2. **Do commercial forks consume `platform-source` (private, with `deploy/`) or
   the public repo?** the internal-tools fork and AIPLA both need the deploy tier, which is the
   commercial value-add. This is a licensing decision, not a technical one.
   Question 3 makes the technical half free — access is granted inside
   `sunholo-data` and reaches nothing of Aitana's — so what remains is purely
   *terms*: who gets `deploy/`, under what licence, and whether it is
   per-repo collaborators or a `sunholo-data` team.
3. ~~**Repo name and org for the source of truth.**~~ **RESOLVED 2026-08-17 —
   `sunholo-data/platform-source`.** Both upstream repos live in `sunholo-data`;
   `Aitana-Labs` holds only the downstream deployment and its customer. The org
   boundary now means something, and granting a commercial fork access no longer
   reaches into the org that holds Aitana's customer work. The old auth trap is
   also gone: the bot turned out to be an active `sunholo-data` org member and
   now has push on the public repo. Repo *creation* still needs
   `MarkEdmondson1234` (member ≠ owner).
4. **What happens to `docs/design/forks/` stubs in this repo?** The the internal-tools fork stub
   exists because eight docs link to it. Under the link-check those links must
   resolve — either keep neutral stubs upstream or update the referrers.
